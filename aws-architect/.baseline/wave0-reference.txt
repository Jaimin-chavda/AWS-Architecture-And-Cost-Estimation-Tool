THREE FINDINGS THE VALID MEASUREMENT SURFACED
---------------------------------------------

1. P2 (applyPatternBaselines) is confirmed empirically, not just by reading.
   EVERY repo that reached the LLM gained the same fixed set on top of its
   real services: ALB, CloudFormation, CloudFront, CloudWatch, Route53,
   SecretsManager. Repo 2 (a Solidity/JS voting app) went from [Route53] to
   9 services, none of which its README supports. Repo 8 went from PASS to
   FAIL purely by acquiring baseline services and losing ECR.

2. The LLM fails schema validation on 25-75% of repos, silently.
   `No object generated: response did not match schema` — console.warn only,
   collapsed to null, no user-visible warning, indistinguishable from a repo
   the LLM legitimately declined. This is exactly P4.1, and it is far more
   frequent than the reports assumed. Wave 1 item 1 must surface it; the
   likely cause is the compose `type: "other"` value (P14) or the prompt's
   hand-written component vocabulary disagreeing with COMPONENT_TYPES (P15).

3. The LLM path drops ECR that the rules path finds (repos 4, 8).
   mapComponentToAws has no ECR emission; ruleEngine does. Independent
   evidence for P3 — the two paths are not comparable, and running only one
   of them loses whatever the other knew. Wave 2 addresses it.
